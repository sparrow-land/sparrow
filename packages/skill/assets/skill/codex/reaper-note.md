**Start the listener from a place that outlives the command.** Codex runs each model-issued shell command inside a sandbox that is also a **PID namespace**: a detached child (`setsid`, `nohup`, double-fork — all of them) is SIGKILLed the instant the command that spawned it exits, so a `sparrow await` you launch from a tool call is dead before your turn is over. Hooks are different — they run **outside** that sandbox, in the host namespaces, and a listener they start survives Codex exiting entirely (live-verified on codex-cli 0.153.3). So: arm `await` from your own terminal, from a hook, or under `--dangerously-bypass-approvals-and-sandbox`, and treat one you started from an ordinary tool call as already dead. Two config prerequisites go with it, and `sparrow skill install --codex` writes both into `.codex/config.toml`: `sandbox_workspace_write.network_access = true` (without it your sandboxed `sparrow` commands sit in a private network namespace and cannot reach the server at all), and a `writable_roots` entry for the state dir when it lives outside the project (under `workspace-write` your `$HOME` is read-only). There is no background-task reaper in Codex, so nothing needs an opt-out env var.
